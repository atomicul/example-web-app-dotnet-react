# Frontend

The React single-page app: Vite, shadcn/ui, TanStack Router and TanStack Query, with an API client generated by
Orval. The [root README](../README.md) covers running and building the app; this one covers the code patterns to
follow when changing the SPA.

## API client

`make api` generates everything under `src/api/generated` from `openapi.json`, the API's OpenAPI document: a TanStack
Query hook per operation, the request and response types, and zod schemas of the request bodies with the API's rules.
Never edit those files; change the API and run `make api` instead.

Every request goes through `fetcher` in `src/api/fetcher.ts`, the client's mutator. It resolves the JSON body, or
throws an `ApiError` for a non-success response, carrying the problem the API sent, or a `NetworkError` when the
request never reached the API.

## Error handling

`errorMessage(error)` turns any failure into a sentence fit for the user: the validation messages when there are any,
the wait asked by a 429, or the error's own message.

`ApiError.errors` lists the validation errors of a 400 from its `issues`, each with the `pointer` to the request
field it is about. Each message is in the user's language when the catalog translates its code under
`validationErrors`, and as the API worded it otherwise (see [Translations](#translations)).

Failed mutations are handled once, in `src/router.ts`:

- Every failed mutation is toasted with `errorMessage`, unless its `meta.handlesErrors` says its caller shows the
  error itself, as a form does under its fields.
- Every settled mutation refetches the active queries under the keys in its `meta.invalidates`, or every active
  query without it, and stays pending until they are refetched, so the page changes once, with the API's data.
- A 429 shows a single shared toast, however many requests it refused, and queries wait for its `Retry-After` before
  their one retry.

```ts
const { mutateAsync: createTodo } = useCreateTodo({
  mutation: {
    meta: { handlesErrors: true, invalidates: [getGetTodosQueryKey()] },
  },
})
```

## Optimistic updates

A change the user expects to take effect at once, as checking a todo does, shows while its mutation is pending,
from the mutation's own `variables`, rather than waiting for the API and the refetch after it:

```tsx
const update = useUpdateTodo({ mutation })
const isComplete = update.isPending
  ? update.variables.data.isComplete
  : todo.isComplete
```

- The mutation stays pending until its queries are refetched (see [Error handling](#error-handling)), so the guess
  gives way to the API's data without flickering back in between.
- A failed mutation stops being pending, so the page shows the data as it was, and the error is toasted. Nothing
  needs undoing.
- Mutations that change the same resource share a `scope` (``scope: { id: `todo-${todo.id}` }``), which runs them one
  after another, so the controls stay enabled and quick changes reach the API in the order they were made.

This suits a change shown in one place, the component that makes it. Once other components show the same data,
write the guess into the cache instead, in the mutation's `onMutate`, and put the cached data back in its `onError`,
as TanStack Query's [optimistic updates](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates)
guide does. `onMutate` first cancels the queries it writes to (`cancelQueries`), so a refetch already on its way,
as from a refresh, doesn't overwrite the guess.

## Forms

Forms use `react-hook-form` with `zodResolver` over the generated schemas, so the SPA checks the API's own rules
before sending:

```ts
const form = useForm({ resolver: zodResolver(CreateTodoBody), defaultValues })
```

- zod words its messages itself, in the user's language. Where its wording explains nothing, as for a `pattern`, a
  form gives its own message per field through `fieldMessages` (`src/lib/field-messages.ts`), as the registration
  form does for the email and password rules. Those messages are the SPA's words: update them when the API's rules
  change.
- A submit handler catches its request's failure with `setServerErrors(form, error)` (`src/lib/server-errors.ts`).
  Validation errors whose pointer names one of the form's fields go under it; every other failure goes to the form's
  root error, which the form shows under its fields. The mutation sets `meta.handlesErrors`, so it isn't toasted too.
- When a page explains a failure in its own words, as login does for unconfirmed or locked-out accounts, it throws a
  `FormError` with the message, which `setServerErrors` shows on the root error.

## Translations

The SPA's texts live in a catalog per language in `src/i18n` (`en.json`, `ro.json`), read through i18next. English is
the reference: `t()` only accepts keys of `en.json`, and a test fails when `ro.json` misses one of its texts.

- Components translate with `useTranslation()`, so they render again when the language changes; code outside them,
  such as `fetcher.ts`, uses `i18n.t` from `@/i18n`.
- Values go in as interpolations, not concatenations: `t('todos.edit', { title })`. Counts use i18next's plural
  suffixes (`_one`, `_few`, `_other`, by each language's rules) and dates its `datetime` format, so both follow the
  language.
- zod's own messages switch to the same language, through its locale in `src/i18n/index.ts`.
- `validationErrors` translates the codes of the API's validation errors. Only other languages need it: English
  falls back to the API's own wording, so `en.json` has none.

The language is the one the user last picked, remembered in this browser, or else the browser's, falling back to
English. Signed-in users pick it in the account menu, and the login, registration and email confirmation pages with
`LanguageSwitcher`. To add one, add its catalog, then list it in `languages` and its zod locale in
`zodLocales` in `src/i18n/index.ts`, and cover it in the catalog test (`src/i18n/i18n.test.ts`).

## Themes

The SPA's colors are the CSS variables shadcn/ui set up in `src/index.css`: `:root` holds the light theme and `.dark`
the dark one, and Tailwind's `dark:` variant applies under the `dark` class. Components use the semantic utilities
(`bg-background`, `text-muted-foreground`, `border-border`) rather than raw colors, so they follow the theme without a
`dark:` variant of their own. To change a color, change its variable in both blocks.

The theme is the one the user last picked in the account menu, remembered in this browser, or else `system`, which
follows the device's light or dark setting as it changes. `src/theme` puts the `dark` class on `<html>`, and
components read the choice with `useTheme()`, as the toaster does. A small script in `index.html` applies the
remembered theme before the SPA loads, so dark pages don't flash white; it reads the same `theme` key in
`localStorage`, so change both together.

## Menus

Menus are built from the parts in `src/components/menu.tsx`, never from `dropdown-menu` or `drawer` directly. On big
screens a menu drops down from its trigger, as shadcn's dropdown menu; on phones, below `useIsMobile`'s 768px, it
slides up from the bottom as a drawer, and each submenu opens as a drawer stacked on it. The parts are named after
shadcn's dropdown menu, so a menu is written once for both:

```tsx
<Menu>
  <MenuTrigger
    render={
      <Button variant="ghost" size="icon" aria-label={t('accountMenu.open')} />
    }
  >
    <CircleUserRoundIcon />
  </MenuTrigger>
  <MenuContent title={t('accountMenu.title')} align="end">
    <MenuSub>
      <MenuSubTrigger>{t('accountMenu.language')}</MenuSubTrigger>
      <MenuSubContent title={t('accountMenu.language')}>
        <MenuRadioGroup value={language} onValueChange={changeLanguage}>
          <MenuRadioItem value="en">English</MenuRadioItem>
        </MenuRadioGroup>
      </MenuSubContent>
    </MenuSub>
    <MenuSeparator />
    <MenuItem onClick={logout}>{t('accountMenu.logOut')}</MenuItem>
  </MenuContent>
</Menu>
```

- `MenuContent`'s `title` names the menu for assistive technology; `MenuSubContent`'s heads its drawer on phones.
- Picking an item or a radio item closes the whole menu, submenus included.
- A label goes in a `MenuGroup`, as the signed-in identity does in the account menu (`src/auth/account-menu.tsx`).
- A part the menu needs and `menu.tsx` lacks, such as checkbox items, is added there for both kinds of menu.

## Pages

Pages are files under `src/routes`, which TanStack Router turns into routes; those under `_authenticated/` require a
session. Their paths form a tree: a page's parent is its path without the last segment, so `/account/email` sits
under `/account`, which sits under `/`. Nest a new page's path under the page it is opened from and goes back to.

Every page but the top one is laid out by `Page` (`src/components/page.tsx`): a back button to its parent and its
title, then its content. Pages fetch what they show in their route's `loader`, as `/account` does, and read it
through query hooks (see [Loading data](#loading-data)):

```tsx
export const Route = createFileRoute('/_authenticated/account')({
  loader: ({ context }) =>
    context.queryClient.query({
      ...getGetPendingEmailQueryOptions(),
      staleTime: 'static',
    }),
  component: AccountPage,
})

function AccountPage() {
  const { t } = useTranslation()

  return (
    <Page title={t('account.title')}>
      <EmailForm />
      <PasswordForm />
    </Page>
  )
}
```

The browser's history follows the same tree, rather than every page visited, so its back button goes up as the
page's does. `withTreeNavigation` (`src/lib/tree-history.ts`) decides what each navigation does to the history,
remembering in each entry the pages behind it:

- Going to a page nested under the current one adds an entry, as opening `/account` from `/` does.
- Going to a page behind goes back to it, dropping the entries after it, so it shows as it was left. A link that
  names search params returns only to an entry with the same ones.
- Going anywhere else replaces the current entry, as opening `/account` from another page does.

Links and `navigate` need nothing special: a plain `<Link to="/account">` follows these rules, and the back button
is a `<Link to="..">`. A page opened directly, from an emailed link or a new tab, has nothing behind it: its back
button replaces it with its parent, and the browser's back leaves the app.

## Loading data

The query cache is the one place a page's data lives. A route's `loader` only fills it, so the page shows with its
data rather than a loading state, and the page's components read the data back through the generated query hooks:

```tsx
export const Route = createFileRoute('/_authenticated/')({
  loader: ({ context }) =>
    context.queryClient.query({
      ...getGetTodosQueryOptions(),
      staleTime: 'static',
    }),
  component: TodosPage,
})

export function TodoList() {
  const { data: todos, isPending, error } = useGetTodos()
  // ...
}
```

The `'static'` `staleTime` makes `query` fetch only what the cache lacks: a page opened again shows at once with what
the cache holds, and the hook's own `staleTime`, React Query's default of 0, refetches it in the background as the
component mounts. Without it, every navigation would wait for a fetch, and the hook would fetch the same data again.

Components never show what a `loader` returns (`Route.useLoaderData()`), nor what a `beforeLoad` puts in the route
context (`Route.useRouteContext()`). Both are snapshots, taken when the route loads, which stay as they were while
the cache changes after them, until the user navigates again. A query hook instead subscribes its component to its
query, which the cache refetches when a mutation invalidates it, when the window regains focus and when the user
refreshes the page, and the component renders again with the new data. This is why the account menu reads the
signed-in user with `useGetApiAuthManageInfo()`, though `_authenticated`'s `beforeLoad` fetched it already.

The route context carries what routes need to decide, not what pages show: `_authenticated`'s `beforeLoad` checks the
session to send the user to the login page, and loaders take the `queryClient` from it.

## Refreshing

A page's data can change while it is open, as when the user edits their todos on another device, so the signed-in
layout lets the user refetch it: by pulling the page down from the top on touch screens (`PullToRefresh`,
`src/components/pull-to-refresh.tsx`, which is the scrolling section under the header), and with the button in the
header elsewhere. The button hides on touch screens (Tailwind's `pointer-coarse:` variant) rather than below a width,
so a tablet pulls and a narrow desktop window keeps the button. Either way, the arrow spins until the refetch is
done, for at least one turn and always whole ones, so a refetch faster than the eye still shows it happened.

Both go through `useRefresh()` (`src/lib/use-refresh.ts`), which refetches the active queries: those a component on
screen reads through its hook. A page needs nothing to take part, as long as it follows
[Loading data](#loading-data):

- Data a component shows from a `loader` or the route context isn't an active query, so a refresh leaves it as it
  was. Running the routes again (`router.invalidate()`) wouldn't help: with its `'static'` `staleTime`, `query` returns
  what the cache holds, however old.
- Queries of the pages left behind aren't refetched. Queries are stale as soon as they are fetched (React Query's
  default `staleTime` of 0), so each refetches anyway once its page shows again.
